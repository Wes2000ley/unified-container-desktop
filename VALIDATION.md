Microsoft WSL 3.0.5 MSI and application MSI/rootfs. Users need one Setup executable.
Windows features and WSL have separate forced-restart boundaries. Full UI offers
Restart or Close; unattended deployment must use `/norestart` to suppress restart.
The main MSI now requires completed prerequisites rather than enabling features
or scheduling an unconditional fresh-install reboot. It grants the installing
Windows user's SID operator membership; SYSTEM installations do not choose an
interactive user. The application remains unsigned.

The earlier share-removal failure was traced to WSL inheriting a working directory inside the mounted drive. Infrastructure commands now select `/` as their working directory; the fresh controlled-share stage in `0135` passed with that change.

The role investigation had two separate access failures. The `0155` isolated ACL probe showed that adding `FILE_READ_ATTRIBUTES` allowed the viewer to open the pipe; its enclosing diagnostic reported failure because it expected all variants, but the individual probe results are recorded. Authenticated users now receive pipe access mask `0x00100083` (data read/write, read attributes and synchronize), without permission to create pipe instances. After that fix, `0165` exposed a service-status query denial: the default controller service DACL granted query access to interactive and service identities, not the batch test user. Provisioning now adds only `SERVICE_QUERY_STATUS` for authenticated users. The client's SCM and server-PID verification remains in place, and the full role retest passed in `0174`.

The pinned WSL 3.0.5 [mirrored-network initialization](https://github.com/microsoft/WSL/blob/3.0.5/src/windows/service/exe/MirroredNetworking.cpp#L224-L234) allocates a guest ephemeral range through the [guest network service](https://github.com/microsoft/WSL/blob/3.0.5/src/windows/service/exe/WslCoreGuestNetworkService.cpp#L112-L173), which calls `HcnReserveGuestNetworkServicePortRange`. A [WSL maintainer explains](https://github.com/microsoft/WSL/issues/12228) that mirrored networking reserves a unique host TCP/UDP range for Linux ephemeral ports. The observed `0257` range containing `52228` and the independent `0259` inside/outside bind sample support the inference that such a reservation caused the Windows bind failure; the reservation handle was not directly inspected. The separate fixture using ports `18880–18883` and explicit Windows NAT subnet `10.203.241.0/24` passed in `0265` and after a controller restart in `0267`. The product did not change the failed fixture's requested port or apply a fallback.

Microsoft documents that NAT networks created on Windows Server 2019 and later are not persisted after reboot; the observed failure above occurred in a separate Windows 11 VM and does not establish the cause of that failure. The pinned Windows Docker NAT driver uses HNS/windowsIPAM, so Docker `default-address-pools` does not control this allocation. [Compose IPAM](https://docs.docker.com/reference/compose-file/networks/) supports explicitly configured subnets; the chosen range and gateway must be evaluated against existing host networks. The deliberate recovery and later reboot passed on the test VM, but no automatic repair or universal result is implied. See Microsoft's [Windows container network driver documentation](https://learn.microsoft.com/en-us/virtualization/windowscontainers/container-networking/network-drivers-topologies) for the platform-specific persistence statement.
