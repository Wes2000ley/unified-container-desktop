# Windows acceptance status

## Current host qualification

The physical host now runs Linux and Hyper-V-isolated Windows containers simultaneously. Installed 0.4.9 passed 69 normal-user CLI checks, 13 combined GUI/Compose workflow groups with the redesigned shared GUI. The 0.4.9 frontend passed 59 frontend tests, 21 browser workflows and two production web-adapter tests; installed 0.4.8 also passed 20 help/output checks. Installed 0.4.7 also passed eight Resource Saver/file-sharing and 15 proxy workflow groups with the same infrastructure implementation. Shared settings round trips, automatic Linux sleep/wake, persistent shares across an engine restart, HTTP/SOCKS5 pulls on both engines, and Buildx/Compose proxy behavior passed with settings restored and owned fixtures removed. Version 0.4.8 introduced the UCD help text. The dated receipts, retained failed trials and current limits are in [VALIDATION.md](VALIDATION.md). The sections below are historical results, not the current installation status. No new host reboot or all-user sign-out is claimed.

## 0.4.0 implementation under test

The 0.4.0 source has been built and is under validation. It covers Linux Resource Saver, administrator-approved Virtual file shares, separate Docker and container HTTP/HTTPS/SOCKS5 proxy settings, Linux subnet and port-binding defaults, address-family modes and DNS inhibition with per-network override, opt-in Linux host networking, and authenticated controller brokering for the GUI and native Docker CLI. The local Go race suite for `./...`, `go vet` and `go mod verify` passed; the frontend check passed 59 tests and the browser fixture suite passed 17 tests. Native VM qualification and development-host installation for 0.4.0 are pending; no live 0.4.0 acceptance pass is claimed.

## 0.3.2 development and host checks

The 0.3.2 source implements a shared machine registry store for the GUI and default native Docker CLI, including a credential helper and `ucd registry` commands; a desktop application and tray icon; live operator-group lookup with roughly five-second raw Docker pipe ACL refresh; personal startup and interface preferences; and activity pagination. The full Go race tests, go vet and go mod verify passed. The build-tagged tests package was not selected. After the streamed registry-build and inventory-refresh fixes, focused Go race tests passed again, frontend check passed 53 tests, the production build passed and all 17 browser fixture tests passed. The first final browser run hit an ambiguous test locator matching both the Engine selector and disk-usage region; the locator now targets the Engine combobox exactly, and the corrected suite passed. All seven application binaries and the MSI built successfully. MSI inspection confirmed version 0.3.2, ALLUSERS=1, the product icon and credential helper, 19 MSI files and 14 hashed payloads. These local checks are separate from the host and VM results below.

On the development host, the authorized 0.3.2 setup exited 0, all 14 installed payload hashes matched and both Docker 29.9.3 engines were online. The overall combined run reported failure at the later VM baseline; its host-upgrade stage passed. In the current non-elevated Windows session, the token still lacked the new operator group but the service identified the user as an operator. The installed CLI queried both engines and Compose and Buildx versions, then passed a real Linux create/start/exec/log/restart and volume-persistence check; the owned container, volume and newly pulled image were removed. The installed production web interface passed a real-bridge check of both engines, shared registry scope, restored interface preferences and activity pagination without JavaScript errors. It had no configured registry sign-in, so this is not an authenticated registry-push test. The production web adapter's two tests also passed. A native desktop check was interrupted by the user's Escape key and is not a pass.

The separate 0.3.2 VM regression failed at the pre-upgrade baseline with `linux project source changed`; the guest report shows no package selected or install tests run, and the VM was shut down. ## 0.1.0 acceptance history

This is a 0.1.0 engineering preview, not a claim of universal Windows qualification. Earlier results used a disposable Windows 11 VM with an installed engineering build whose controller was refreshed during development. A later normal uninstall of the existing product followed by installation of the tested MSI registered the product and required a reboot; two separate network probe workloads recovered, but the core Windows workload failed to restart. An administrator deliberately recovered that workload using an explicit subnet, and both core workloads passed a later VM reboot. Installed runtime, standard roles and browser reruns passed, but a subsequent Windows TCP listener verification failed. The observed WSL ephemeral range and a separate bind comparison support a reservation explanation; a new outside-range fixture passed in the VM. The installer suite passed after a real reboot, and restored canonical package, helper, port and browser checks passed. Raw reports are retained under `work/ucd-acceptance-vm/responses` on the development machine and are not part of the product MSI. The release ZIP includes selected JSON under `acceptance-evidence/`. Check any MSI against its accompanying `dist` checksum sidecar.

## Port and support boundaries

Managed Windows Compose publication uses controller-owned TCP/UDP listeners that forward to one usable container NAT endpoint. The original YAML remains unchanged. A missing or multiple NAT endpoints or a listener bind error is reported. The implementation accepts up to 1,024 published port entries per Windows container; a UDP listener holds up to 1,024 client sessions, expires idle sessions after 60 seconds, and drops new sessions when full. Omitted host addresses default to loopback. Linux publication uses Docker and mirrored WSL networking. Dynamic long-form published ranges are rejected.

Microsoft documents that NAT networks created on Windows Server 2019 and later are not persisted after reboot; the observed failure above was on a Windows 11 VM. The pinned Windows NAT driver uses HNS/windowsIPAM, so Docker `default-address-pools` does not control its address allocation. [Docker Compose IPAM](https://docs.docker.com/reference/compose-file/networks/) supports an explicit `networks.default.ipam.config` subnet and gateway; choose values after checking the host's existing networks and routes. The tested explicit-subnet recovery is specific to that VM. See [Microsoft's Windows container network driver documentation](https://learn.microsoft.com/en-us/virtualization/windowscontainers/container-networking/network-drivers-topologies) for the persistence boundary.

The product MSI and binaries are unsigned. Obtain the package and expected checksum through a trusted channel. A standalone Windows Engine on Windows 11 is outside Microsoft's documented Docker Desktop support configuration; these tests do not create a Microsoft or Docker support guarantee.
